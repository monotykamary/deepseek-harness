# Agent Note：DSH 应用拥有经过测试的发行版

Status: implemented

[English](2026-08-12-cohesive-distribution.md) | 中文

## 问题

内置配置档曾把 Bundle 名称与用户管理的配置档存储在同一字段中。启动器只能识别少量历史精确元组；Fabric 与 Fovea 加入后，它无法区分当前安装拥有的层与用户配置。因此 DSH 可执行文件更新后，配置档或独立版本范围内的配套插件仍可能陈旧。

安装也没有统一的版本清单。npm、npx、Nix 与源码检出需要不同更新操作；通用更新按钮可能替换错误的安装，或在包管理器仍是权威来源时误报成功。

## 决策

`@monotykamary/dsh` 应用是一套经过测试的发行版。其清单固定 Fabric 与 Fovea 的精确版本，并在 `dsh.distribution.companions` 下记录相同版本；发行验证拒绝两处漂移。内置配置档保存 `dsh.profile.template` 与用户管理的 `bundles`。启动器每次启动都从自身安装解析当前模板，并迁移已识别的历史前缀，同时保留追加的用户 Bundle。

`@monotykamary/dsh-distribution-update` 投影已安装包版本，缓存有界 npm Registry 检查，识别安装渠道，并向 CLI 与 Web 设置公开状态。npm 全局安装与源码检出会启动分离 Worker；源码渠道变更由[自动单调更新决策](../bug-fix/2026-08-22-automatic-monotonic-source-updates.zh.md)负责。Worker 移除类似凭据的环境变量，写入仅所有者可读的状态，且不重启 Harness。Nix、npx 与未知渠道返回外部管理指引。

设置 Consumer 注册更新页面与现有设置入口内的 Badge 席位。Registry 失败是面向操作者的诊断，而不是应用启动失败。

## 测试

配置档测试覆盖新模板清单、两种历史元组迁移、追加用户 Bundle 的保留、未知模板与重复层。发行版测试覆盖渠道识别、已安装闭包清单、Registry 成功与失败、并发请求折叠、缓存状态及 npm 全局安装之外的分离启动拒绝。CLI 测试覆盖所有新命令解析与 JSON 输出路径。组装后的 Web 快照通过真实配置档组合覆盖更新区段与设置 Badge。

## 考虑过的替代方案

**在每个配置档中保留完整内置元组。** 拒绝，因为首次自定义后，元组相等无法区分陈旧的托管配置档与用户有意组合。

**让每个配套插件独立跟随 latest 标签。** 拒绝，因为最新不代表彼此经过测试。应用发行清单是兼容性权威。

**在 Host 进程内直接运行 npm。** 拒绝，因为替换已加载的包文件具有平台差异，并把安装生命周期耦合到运行中的 Harness。分离 Worker 独立拥有安装并报告完成。

**为所有渠道提供自更新。** 拒绝，因为 Nix 与源码安装属于外部状态管理器，而 npx 调用本身可丢弃。DSH 显示正确命令，不获取不属于自身的所有权。

## 后果

更新应用会更新默认配置档栈，无需编辑用户配置。用户添加的 Bundle 与补丁层在发行版之间保持稳定。配套插件版本只有在 DSH 发行版固定并测试后才对 DSH 可用。

Registry 检查会为 Web 配置档增加有界后台网络流量。操作者可在后续补丁层修改 Registry、间隔、启动行为与超时。npm 全局更新需要显式操作与手动重启；回滚仍由包管理器负责。
