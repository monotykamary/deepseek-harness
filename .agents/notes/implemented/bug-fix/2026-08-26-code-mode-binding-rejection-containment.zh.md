# Agent Note: Code Mode 绑定拒绝收容

Status: implemented

[English](2026-08-26-code-mode-binding-rejection-containment.md) | 中文

## 问题

CodeRuntime 可能调用一个 `run_code` 绑定，随后在不保留返回 Promise 的情况下结算其 guest。生成的代码省略 `await`、复合 guest 操作提前结算，或运行时清理丢弃待处理 host 调用时，都可能出现这种情况。桥接层仍必须中止并排空其嵌套调用。此时，进行中的绑定会以 `result discarded` 拒绝，排队且尚未启动的绑定则以 `tool call abandoned` 拒绝。

对于等待绑定的运行时，这些拒绝是正确结果。但运行时已经丢弃 Promise 时，同一拒绝会作为 `unhandledRejection` 到达 Node。应用启动的 fail-loud 处理器会有意把其他情况下无人负责的每个拒绝视为致命错误，因此一个格式错误的 `run_code` 程序可能在运行已经结算后终止长期运行的 `dsh web` 进程。

## 决策

绑定工厂启动一个分发操作，立即为该操作附加拒绝观察器，并原样返回原始 Promise。观察器只负责 host 进程收容：它不会返回替代 Promise、把拒绝转换成成功，也不会更改错误。因此，等待调用的运行时仍会收到与以前相同的工具失败、结果丢弃失败或排队放弃失败；丢弃调用的运行时则不再留下无人负责的进程级拒绝。

调度器保留既有结算纪律。运行结算会中止活跃调用，放弃排队且尚未启动的调用，排空已启动调用及其有序提交，仅为已启动调用记录事件，并只在这些自有操作完全停稳后返回。

## 考虑过的替代方案

**让进程 fail-loud 处理器忽略放弃消息。** 拒绝，因为该全局处理器无法证明哪个拒绝可以安全分离；按消息过滤会隐藏其他插件的真实生命周期缺陷。

**让已丢弃或已放弃的绑定成功解析。** 拒绝，因为等待绑定的调用方不得从未运行的工作或属于已结束运行的结果中观察到值。

**要求每个 CodeRuntime 保留每个绑定 Promise。** 拒绝作为唯一防线，因为提供方清理和格式错误的 guest 代码仍可能丢弃调用。核心桥接层创建该拒绝 Promise，可以在不削弱提供方可见语义的情况下收容它。

## 后果

- 丢弃的进行中和排队绑定 Promise 无法在 `run_code` 排空期间到达 `process.unhandledRejection`。
- 被等待或显式捕获的绑定保留其确切拒绝消息。
- 进程 fail-loud 策略对所有真正无人负责的拒绝保持严格。
- 聚焦回归测试使用一个故意丢弃两个调用的运行时，证明结果丢弃与排队放弃均受到收容；既有的捕获放弃测试证明原始 Promise 仍原样拒绝。
